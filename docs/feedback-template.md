# Beta Feedback Template

Use this template only with synthetic fixtures. Do not include names, contact
details, school identifiers, raw parent messages, screenshots with identifiers,
API keys, tokens, or local configuration files.

This template does not create adoption, external-review, or release evidence by
itself. The maintainer records a claim only after a dated, consented, and
verifiable source exists.

## Tester record

- As of date: YYYY-MM-DD
- Source type: beta tester | adopter | external evaluator
- Relationship to project: non-author | contributor | other
- Consent to summarize this finding publicly: yes | no
- Consent scope: anonymous summary only | public profile or project URL | none
- Environment: operating system and Node version
- Setup path used: clone and mock CLI | other
- Actual duration: from clone to first successful mock output
- Outcome: completed | blocked | partial
- Command that failed, if any: exact command only; redact personal data
- Error summary: redact paths, account names, and credentials
- Most confusing step:
- Most useful output or workflow:
- Suggested improvement:
- Potential reuse scenario: describe without a person, school, or student
- Related issue, PR, or release URL: URL or not recorded
- Maintainer triage: triaged | fixed | deferred | not reproducible | not recorded

## Maintainer handling

1. Store a consented anonymous summary in the evidence process only when the
   tester selected yes.
2. Turn a reproducible defect into a real issue with source type and triage
   details; do not label a maintainer-created request as external feedback.
3. Link a verified fix to a PR and release only after both events occur.
4. Keep a no-consent finding private and out of public evidence documents.
